GWS 검증 시나리오 2 고급 ADV-01

Google Apps Script 웹 앱 기반 사내 신청·결재 시스템 구축

Apps Script 웹 앱과 HTML 서비스를 활용하여 사내 신청·결재 화면을 구축하고, 권한 설정 및 배포 파이프라인을 운영하는 방법을 습득합니다.

대상 서비스
Google Apps Script, Google Sheets, Gmail
필요 에디션
제한 없음 Apps Script 는 전 에디션 · 개인 계정 일부 제약
예상 소요
120분
난이도
상

사전 준비

  • 역량JavaScript 기본 문법과 HTML/CSS. Apps Script 는 서버측 JS 이므로 Node 경험이 있으면 수월합니다
  • 계정개발자 1개 + 신청자 역할 계정 2개 + 결재자 1개. 배포 방식별 동작 차이를 보려면 최소 4개가 필요합니다
  • 권한관리 콘솔에서 Apps Script 와 웹 앱 배포가 허용되어야 합니다. 차단 시 배포 메뉴가 비활성입니다
  • 주의동시 쓰기 테스트(Step 10)에는 계정 여러 개 또는 스크립트 기반 부하 발생이 필요합니다. 순차 20건은 검증이 되지 않습니다

단계별 수행 전체 9단계

01

Google Drive 또는 script.google.com에서 신규 Apps Script 독립형 프로젝트를 생성하고, 서버 측 로직을 다루는 Code.gs와 클라이언트 UI 구조를 정의하는 Index.html 파일을 작성합니다.

확인 프로젝트에 Code.gs 와 Index.html 이 생성되고 편집기에서 전환됩니다.
02

웹 앱 요청 진입점인 doGet(e) 함수를 구성하고, HtmlService.createTemplateFromFile()을 활용하여 동적 데이터 바인딩이 가능한 신청 양식 HTML 화면을 렌더링 및 반환합니다.

doGet 은 웹 앱의 진입점입니다. 이 함수가 없으면 배포해도 404 가 반환됩니다.

확인 테스트 배포 URL 로 접속했을 때 HTML 화면이 렌더링됩니다. 404 면 doGet 이 없거나 이름이 틀린 것입니다.
03

google.script.run 클라이언트 API를 통해 페이지 새로고침 없이 서버 측 스크립트 함수를 비동기 호출하도록 구현하고, withSuccessHandler 및 withFailureHandler 콜백 핸들러를 구성합니다.

확인 클라이언트에서 호출한 서버 함수가 실행되고 withSuccessHandler 로 결과가 돌아옵니다.
04

제출된 신청서를 Google Sheets DB에 기록하는 서버 함수를 구현하고, LockService.getScriptLock()을 적용하여 다수 사용자의 동시 데이터 제출 시 발생할 수 있는 데이터 경합(Race Condition)을 방지합니다.

확인 Sheets 에 행이 추가되고, LockService 획득 실패 시 예외가 발생합니다.
05

Session.getActiveUser().getEmail()로 접속자 계정을 식별하고 인사/조직 정보 연동을 통한 자동 결재선 지정 로직을 구현합니다. (외부 사용자 접속 제한 조건 및 실행 주체 권한 설정 병행 검증)

문서에 명시된 함정입니다. '나로 실행' 으로 배포하면 Session.getActiveUser().getEmail() 이 동일 도메인이 아닐 때 빈 문자열을 반환합니다. 결재선 분기가 통째로 무너집니다.

확인 신청자 이메일이 빈 값이 아닌 실제 주소로 찍힙니다. 빈 값이면 배포 방식 문제입니다.
06

배포 관리 메뉴에서 '웹 앱' 유형을 선택하고, 웹 앱 실행 주체(나 또는 앱에 액세스하는 사용자) 및 접근 권한 범위를 내부 조직 및 대상 그룹에 맞게 설정합니다.

실행 계정과 액세스 범위 조합이 동작을 결정합니다. '나로 실행' + '모든 사용자' 는 편리하지만 신청자 식별이 불가능해집니다.

확인 배포 후 웹 앱 URL 이 발급되고, 실행 계정·액세스 범위가 요약에 표시됩니다.
07

개발 테스트용 디버깅 URL(/dev)을 통해 기능 검증을 진행한 후, 정식 라이브 환경을 위한 버전 스냅샷 기반 Production URL(/exec)을 새로 배포하여 운영 환경을 분리합니다.

확인 /dev 는 코드 저장 즉시 반영되고, /exec 는 새 버전을 배포해야 바뀝니다.
08

appsscript.json 매니페스트 파일의 oauthScopes 항목을 구성하여 Sheets, Gmail 등 서비스에 필요한 최소한의 OAuth 범위만 명시적으로 지정하여 권한을 최적화합니다.

확인 OAuth 동의 화면에 매니페스트에 적은 범위만 나열됩니다.
09

결재 승인 또는 반려 처리 시 GmailApp 서비스로 결재 결과를 신청자에게 자동 통보하고, Google Sheets 내 승인 상태, 처리자, 처리 일시 타임스탬프를 실시간으로 갱신합니다.

확인 승인·반려 시 신청자에게 메일이 도착하고 이력 시트에 행이 추가됩니다.

확인 방법 최종 결과 2개

신청서 20건을 동시에 제출해도 누락·중복 없이 정확히 20행이 저장되어 데이터 정합성 100%를 유지합니다.

실행 기록에 스크립트 오류가 남지 않아 실행 오류율이 0%입니다.

자주 겪는 오류

배포 URL 로 접속하면 404
doGet 함수가 없거나 이름이 틀린 경우입니다. 웹 앱 진입점은 doGet(GET)·doPost(POST) 로 이름이 고정되어 있어 바꿀 수 없습니다. 대소문자도 정확해야 합니다.
신청자 이메일이 빈 값으로 옴
'나로 실행' 배포에서 동일 Workspace 도메인이 아닐 때 발생합니다. 예외 없이 빈 문자열이라 조용히 넘어갑니다. '사용자로 실행'으로 바꾸거나, 빈 값일 때 명시적으로 예외를 던져야 합니다.
코드를 고쳤는데 반영이 안 됨
/exec 는 배포된 버전을 실행합니다. 저장만으로는 바뀌지 않고 새 배포가 필요합니다. 개발 중에는 저장 즉시 반영되는 /dev URL 을 쓰세요.
동의 화면 권한이 과도하게 넓음
매니페스트에 oauthScopes 를 적지 않아 자동 추론된 것입니다. 필요한 범위만 명시하세요. spreadsheets 대신 spreadsheets.currentonly 처럼 좁은 범위가 있는지 먼저 확인합니다.
동시 제출 시 행이 덮어써짐
getLastRow() 로 위치를 계산하고 쓰는 구조는 경쟁 조건에 취약합니다. LockService.getScriptLock() 으로 감싸고, appendRow 처럼 원자적 API 를 쓰면 안전합니다.
'사용자로 실행'인데 시트 접근 오류
각 사용자에게 대상 시트 권한이 없기 때문입니다. 시트를 전원에게 공유하거나, 신청자 식별은 '사용자로 실행'으로 하고 저장은 별도 라이브러리·API 로 분리하는 설계를 검토합니다.
